## 1. 产品定位

本项目是面向天窗、天幕、阳光房、遮阳等定制业务的单用户销售 CRM，重点解决以下问题：

- 把线索、客户、商机、报价、订单、售后和物流放在一条业务链上管理。
- 用产品主档和 Excel 下单表统一产品配置，减少临时拼表、重复录数和报错。
- 让客户确认的报价单成为唯一可下单依据，保留可追溯的产品和价格快照。
- 通过跟进提醒、客户 360、工作台和统计，降低漏跟进、漏收款和漏售后。
- 支持内网服务器部署、移动端访问、数据库备份和后续数据迁移。

当前使用边界：

- 单用户、单组织，不做角色权限体系。
- 主要服务销售本人，不包含生产排程、工厂工单和财务系统。
- 生产、财务确认和货物运输在系统外发生，系统只记录业务状态和结果。

## 2. 用户目标与成功标准

| 目标 | 成功标准 |
| --- | --- |
| 不遗漏线索 | 新线索能录入、去重、跟进、失效或转化；转商机后仍有完整履历 |
| 快速完成报价 | 可直接使用产品模板，上传改好的 Excel 后自动识别金额并生成预览图 |
| 减少报错和错单 | 客户只确认一张报价单；确认后才可下单；产品参数和下单表版本可追溯 |
| 收付款清楚 | 产品合计、整单优惠、产品应收、运费、订单应收、定金、尾款分开计算 |
| 知道今天做什么 | 工作台突出今日和逾期跟进、销售进展、订单待办与售后风险 |
| 售后有闭环 | 一张订单可关联多张售后单；记录处理过程，完成后不可重开 |
| 数据可保护 | 登录、会话、附件访问、备份、软删除和数据库迁移有明确规则 |

## 3. 业务主流程

```text
线索
  ├─ 正常维护 / 标记失效
  └─ 转客户并建立首个商机
          ↓
        客户
          ├─ 档案、联系人、地址簿、客户 360
          └─ 转商机
                  ↓
                商机
                  ├─ 一张或多张报价单
                  ├─ 产品主档 + 本次 Excel 下单表
                  └─ 客户确认唯一一张报价单
                              ↓
                            订单
                        待支付 → 已支付定金 → 生产中
                        → 已支付尾款 → 待发货 → 已发货 → 已完成
                              ↓
                            售后
                        待处理 → 处理中 → 已完成
```

## 5. 详细需求与验收标准

### REQ-AUTH-001 · 登录与会话

**需求**

- 系统只服务单一业务用户，但必须登录后才能访问业务接口。
- 会话有效期固定 12 小时，不随请求滑动；重新登录后恢复金额遮罩默认状态。
- 支持修改显示名和密码。

**验收标准**

- 未登录访问业务接口返回 `401`，页面回到登录状态且不出现空白业务表格。
- 登录成功后会话 Cookie 为 `HttpOnly`、`SameSite=Lax`，有效期 12 小时。
- 退出登录后原会话失效。
- 生产日志和健康检查不暴露密码或数据库凭据。

### REQ-LEAD-001 · 线索录入、编辑、搜索与去重

**需求**

- 新线索至少要有姓名和手机号；微信为选填，但可正常保存和搜索。
- 手机号是有效线索的唯一业务键；不同线索不能重复占用同一有效手机号。
- 支持姓名、来源、类型、公司、地区、微信、手机、标签、意向、备注等字段。
- 来源、类型、意向等选项由数据字典提供，前端不硬编码业务文案。
- 搜索支持姓名、手机号、微信、地区等模糊匹配；前后空格忽略，`%`、`_` 等按普通字符处理。
- 列表支持状态页签、搜索、分页和最近更新时间或创建时间排序。

**验收标准**

- 缺姓名返回业务错误 `name_required`；缺手机号返回 `phone_required`。
- 重复有效手机号不写入新记录，并提示已有线索或客户。
- 搜索 `%`、`_`、引号或分号不会返回全表，也不产生 SQL 错误。
- 编辑后列表和详情立即显示新值，搜索条件与状态页签可组合。

### REQ-LEAD-002 · 线索跟进、标签、失效与批量导入

**需求**

- 首次真实跟进后，线索状态从“新线索”变为“跟进中”。
- 已转化、已失效线索不可继续作为正常销售线索跟进。
- 线索可标记失效；失效原因必选，“其他”必须补充说明。
- 支持快捷标签与批量标签编辑；标签变更只形成一次有效履历。
- 支持 CSV 模板下载、字段映射、预览、整批校验和导入。

**验收标准**

- 跟进内容不能为空，下次跟进时间可为空；日期格式必须合法。
- 标签为空或超出上限时给出可读错误，终态线索不可改标签。
- CSV 中来源不在当前字典、姓名缺失、手机号重复或联系方式不完整时，整批拒绝，不产生部分数据。
- 导入成功后，每条记录都有创建履历，意向默认“中”，页面可立即搜索。

### REQ-LEAD-003 · 线索转客户并建立首个商机

**需求**

- 线索转化后自动建立客户和首个商机，原线索归档为“已转化”，不再出现在线索池。
- 客户继承线索的来源、地区、备注、标签、意向等级、历史跟进和创建时间。
- 命中已有客户时，用户可关联已有客户或明确选择强制新建。
- 公司线索转客户时，主联系人迁移到客户联系人表。

**验收标准**

- 正常转化同时得到客户、商机和完整关联关系。
- 新商机进入“报价”阶段，产品、尺寸、手动/电动和金额等业务字段完整。
- 已转化线索不能重复转化。
- 关联客户不匹配、联系方式缺失或商机关键字段非法时返回明确错误。

### REQ-CUST-001 · 客户档案、联系人、地址簿与客户 360

**需求**

- 客户页面不提供常规“新建客户”入口，客户由线索转化产生；接口保留兼容能力。
- 客户记录类型、地区、来源、意向、标签、备注、画像和创建时间。
- 公司客户支持 0～N 个联系人，最多一个主联系人。
- 客户地址簿支持新增、编辑、删除和默认地址；订单保存收货快照，不受地址后续修改影响。
- [用户明确要求，2026-11-09] 生成订单和修改订单时，可从该客户在 `customer_addresses` 中的历史收件人及地址中选择一条，自动填充收货人、电话和地址；手填新地址仍可回存地址簿。
- 客户 360 汇总档案、标签、商机、订单、售后、跟进时间线和统计。
- 客户生命周期自动派生为潜在客户、商机中、已成交或复购。

**验收标准**

- 客户详情可在同一页查看关键业务关系和渐进展开的履历。
- 地址被修改或删除后，历史订单仍显示下单时的收货信息。
- 联系人可按手机号或姓名搜索，公司客户转化后主联系人可查。
- 删除重要业务引用前有保护，不留下无法解释的孤立页面。

### REQ-PROD-001 · 产品主档和单品 Excel 下单表

**需求**

- 一份产品对应一份 `.xlsx` 下单表；产品编码由系统生成，初始目录使用 `TS-001` 起。
- 产品主档记录名称、分类、系列、结构、开启方式、驱动、型材、扇型、带边情况、规格范围和附件标签。
- 产品文件保存原文件名、大小、存储键和 SHA-256；可下载、替换和追溯版本。
- 没有有效 Excel 的产品不能被新商机报价选择。
- 需要为新上传的下单表提供识别、预览和确认流程。

**验收标准**

- 初始产品目录可幂等补齐；已删除的产品不会被下一次启动自动恢复。
- 产品文件只接受允许的 Excel 类型，单文件不超过 20MB。
- 产品名称和编码可追溯；历史商机或订单不因主档改名或替换文件而改变。
- 新商机只能选择启用且下单表可用的产品。

### REQ-DEAL-001 · 从客户或线索建立商机

**需求**

- 商机只能从线索或客户进入，不提供脱离来源的直接新建入口。
- 线索转商机时，转化确认只负责建立客户和空商机备注，不再要求产品、尺寸或金额；报价信息在报价单中维护。
- 客户转商机同样先建立商机，再在商机内创建报价单。
- 商机支持手动标签和系统标签；系统标签不提供删除入口。

**验收标准**

- 没有线索或客户来源时，商机新建页拒绝进入并给出返回入口。
- 商机创建后初始阶段为“报价”。
- 商机客户的链接可正确返回客户详情。
- 商机记录不展示已废弃的独立备注编辑入口作为核心流程。

### REQ-QUOTE-001 · 多报价单、多产品明细和报价状态管理

**需求**

- 一个商机可创建多张报价单，用于比较不同产品方案。
- 每张报价单包含标题、状态、备注和至少一条产品明细。
- 报价单状态为：`draft` 报价、`pending` 待客户确认、`confirmed` 客户已确认、`void` 历史（内部兼容状态名为 `void`）。
- “待客户确认”可退回“报价”重新编辑；客户已确认或历史报价单不能退回或删除。
- [用户明确要求，2026-11-09] 客户确认一张报价单时，同一商机其他报价单立即自动转为历史；历史报价单只读，不能添加产品、发送、确认、重新报价、作废、删除或关联新的跟进。
- [用户明确要求，2026-11-09] 商机中的报价单按“客户已确认 > 待客户确认 > 报价 > 历史”排序，同状态按更新时间倒序排列。
- [用户明确要求，2026-11-09] 客户确认后，商机操作区不显示“添加报价单”和“标记流失”，只保留“生成订单”；未确认前的报价维护入口保持可用。
- 一个商机最多只能有一张客户已确认报价单。
- 报价单发送客户确认时，生成“待确认”和金额等自动标签；客户确认后同步商机阶段。

**验收标准**

- 草稿报价单可增删改产品，待确认和已确认报价单的关键字段锁定。
- 发出待确认前，所有产品明细都有有效下单表。
- 同一商机第二张客户已确认报价单被拒绝。
- 客户确认后，其他报价单状态显示为“历史”，相关报价单写接口均被拒绝。
- 报价单列表严格按确认、待确认、报价、历史分组，同组内最新更新在前。
- 报价单、自动标签、商机阶段和商机保存金额保持同步。

### REQ-QUOTE-002 · Excel 下单表校验、金额识别和预览

**需求**

- 报价产品只接收 `.xlsx`，单文件不超过 20MB。
- 只读取第一个工作表 `Sheet1`，其他工作表忽略。
- 用 `Sheet1!A1` 与所选产品原始模板比对；不一致时禁止保存。
- 自动识别包含“合计”“总计”“总金额”的区域中大于 0 的金额，预填报价，允许人工调整。
- 生成保留表格样式和关键行列内容的数据区图片，供商机页缩略图和历史查看。
- 保存上传版本，后续替换文件不能覆盖历史快照。

**验收标准**

- 非 `.xlsx` 返回 `quote_form_xlsx_required`。
- 产品模板不匹配返回 `quote_form_product_mismatch`，不落库。
- 金额调整不要求重新上传原始文件，识别合计和最终报价分开保存。
- 历史下载始终返回当时上传的具体版本。
- 预览图中文字、合并单元格、行列宽高和边框可见且可点击放大。

### REQ-ORDER-001 · 由客户确认报价单生成订单

**需求**

- 只有客户已确认的报价单可生成订单，且每张报价单只能生成一张订单。
- 订单产品、数量、单价、产品快照、生产参数和下单表均复制自确认报价单。
- 生成订单时填写整单优惠、优惠原因、运费、定金、物流和收货信息。
- 订单新增“订单名称”；生成订单时自动继承客户已确认报价单的名称。
- 生成订单表单显示订单名称；产品展示只显示产品名称，不显示产品编号。
- 优惠只作用于产品合计，不能冲抵运费；运费独立计入订单应收。
- 商机生成订单后即为存档状态，页面显示“已生成订单”；商机主体、备注、关联报价数据和已有标签均只读，只能查看，后续沟通记录到订单或售后。

计算公式为：

```text
产品合计 = Σ（明细单价 × 数量）
产品应收 = 产品合计 - 整单优惠
订单应收 = 产品应收 + 运费
尾款 = 订单应收 - 定金
```

约束：

- `0 ≤ 整单优惠 ≤ 产品合计`
- `运费 ≥ 0`
- `0 ≤ 定金 ≤ 订单应收`
- `订单应收 = 定金 + 尾款`

**验收标准**

- 未确认报价单生成订单返回 `quote_not_confirmed`。
- 重复生成订单被拒绝，商机保持锁定。
- 已生成订单商机的编辑、记跟进、添加/删除标签、添加报价和标记流失接口均拒绝写入，商机、报价和标签数据保持不变。
- 生成订单时复制产品、价格、参数和下单表快照，之后不能通过修改报价单或商机反向改变订单。
- 已生成订单的商机详情不显示不可执行的按钮，只保留查看订单、展开报价明细和打开附件等查看入口。
- 优惠超额返回 `invalid_discount`，且不产生订单、不走半截状态。
- 新报价单流程生成的订单直接进入“待支付”。
- 订单详情分开展示产品合计、整单优惠、产品应收、运费、订单应收、已收和未收。
- 订单详情头部的主标题显示订单名称，订单编号作为辅助信息展示。

### REQ-ORDER-002 · 订单收款、状态、物流和履历

**需求**

- 活跃订单状态为：待支付 → 已支付定金 → 生产中 → 已支付尾款 → 待发货 → 已发货 → 已完成。
- 订单只能逐步推进，不得越级或回退；取消、退款和退货通过售后处理。
- 定金、尾款按应收金额收款，支持支付截图；未收齐不能完成订单。
- 物流方式为包邮、代办、自提；自提可隐藏承运和收货要求，包邮和代办按业务规则校验。
- 物流公司支持多联系人，可停用；已被订单引用的公司不能删除。
- 订单记录发货信息、收货快照、状态日志和完整时间线。
- 订单名称可由用户修改；订单编号由系统生成，禁止用户修改。

**验收标准**

- 非法跳转返回 `invalid_transition`。
- 实收金额与本次应收不一致时拒绝，订单状态和已收金额均不变化。
- 未收齐时完成订单返回 `payment_incomplete`。
- 发货前必须有运单号；自送或无物流场景允许业务约定值“无”。
- 已完成订单隐藏普通编辑入口，必要修改必须保留履历。
- 修改订单名称时写入订单履历；请求修改订单编号必须被拒绝，原编号保持不变。

### REQ-FOLLOW-001 · 五类业务对象统一跟进与附件

**需求**

- 跟进可挂在线索、客户、商机、订单或售后单上。
- 跟进方式为微信或电话，默认微信；内容必填。
- 支持下次跟进日期开关；关闭后该条记录不参与待办提醒。
- 单条跟进最多 10 个附件，单个文件不超过 20MB。
- 图片显示缩略图并可当前页查看大图；Excel、PDF、Word、图纸等显示文件条。
- 创建、编辑、阶段变化、报价、下单、客户确认、收款、发货、修改收货等系统事件进入统一履历。

**验收标准**

- 无效对象类型返回 400；不存在或已锁定对象的跟进按业务规则拒绝。
- 一条跟进超过 10 个附件时给出明确提示，不产生部分附件记录。
- 附件路径穿越、非法扩展名和内联执行风险有防护。
- 历史版本、金额和备注不因字典改名或主档修改而失真。

### REQ-AFTER-001 · 订单售后流程与 SLA

**需求**

- 售后只能由已完成订单发起，一个订单可关联多张售后单。
- 售后类型为退货、换货、维修、投诉、其他。
- 状态为待处理 → 处理中 → 已完成。
- 记录第一条跟进后自动进入“处理中”；不提供“拒绝”和“重新打开”。
- 完成后记录结果和完成时间，不可再添加跟进；再次维修需另开售后单。
- 待处理超过 3 天进入工作台风险提醒。
- 新建售后可关联同一订单中已完成的上一张售后单。

**验收标准**

- 未完成订单创建售后返回 `order_not_completed`。
- 待处理售后添加跟进后状态自动变为 `processing`。
- 已完成售后添加跟进返回 `aftersale_closed`。
- 关联售后必须属于同一订单且已完成，否则拒绝。

### REQ-DASH-001 · 工作台待办与经营概览

**需求**

- 工作台优先展示今天需要做什么，不作单纯数据大屏。
- 聚合今天到期和逾期的最近跟进，逾期需要醒目标识。
- 待跟进以同一对象最近一条真实跟进的 `next_date` 为准；新跟进覆盖旧提醒。
- 展示进行中商机、本月成交、本月新增客户、订单待办、近日动态和售后风险。
- 售后工作概览只统计和展示未完成售后单（`pending` 待处理、`processing` 处理中）；已完成和已拒绝售后不进入“进行中售后”数量或“售后提醒”列表。
- 金额默认遮罩，用户主动显示后仅在同一登录会话内保持。

**验收标准**

- 新跟进产生更晚日期后，旧待办自动消失。
- 已确认或已作废的商机关联跟进不进入普通待办。
- 点击数字卡和待办行可进入带正确筛选条件的列表或详情。
- [用户明确要求，2026-11-05] 点击“今日待跟进”和“已逾期”数字卡时，在当前工作台滚动到“今日待跟进”区域，不跳转独立跟进表单；其他数字卡仍进入对应业务列表。
- [用户明确要求，2026-11-05] 今日待跟进行右侧操作为“跟进”，点击后直接进入该条跟进关联的商机详情；没有关联商机时进入客户详情。工作台不再弹出快捷跟进表单。
- [用户明确要求，2026-11-05] 第四张数字卡命名为“进行中售后”，显示所有未完成售后单的准确数量；“售后提醒”只展示最近未完成售后单。
- 375px 手机宽度下无横向滚动，关键待办可在一屏内看到。

### REQ-DICT-001 · 可维护的业务数据字典

**需求**

- 字典按维护能力分级：
  - A 类：可新增、改名、排序和停用。
  - B 类：可改名和排序，不能增删状态项。
  - C 类：只可改名。
  - D 类：只读。
- 当前核心字典包括产品型号、客户来源、意向等级、产品类型、商机流失原因、售后类型、跟进方式、商机阶段、订单状态、售后状态、客户类型和跟进对象。
- 数据只保存英文 key，中文标签由字典或标签映射生成。
- 被业务数据引用的选项只能停用，不能删除。

**验收标准**

- 新增“抖音”等来源后，刷新页面即可在相关下拉中看到，无需改代码或重启。
- 已停用选项不出现在新表单，但历史列表仍可显示中文名。
- B/C/D 级越权新增或删除被拒绝。
- 修改显示名后历史数据同步显示新名称。

### REQ-STAT-001 · 销售与订单统计

**需求**

统计至少覆盖：

- 客户总数、本月新客、进行中商机、本月成交、复购和待处理售后。
- 近 6 个月成交趋势。
- 商机漏斗，按累计到达口径计算。
- 线索转化状态和转化率。
- 商机阶段分布、订单状态分布、客户来源、售后类型。
- 型号带出的尺寸只作初值，统计以商机实际尺寸和实际金额为准。

**验收标准**

- 漏斗中的待确认和客户已确认包含已到达的前序阶段，作废商机不计入漏斗。
- 线索转化率不超过 100%。
- “本月”按 Asia/Shanghai 当前自然月计算，不做 UTC 跨日错位。
- 金额以两位小数汇总，前端根据隐私遮挡状态显示。

### REQ-UI-001 · 移动端、金额遮罩和缓存一致性

**需求**

- 页面同时适配桌面和手机，表单使用紧凑双列布局，长字段独占整行。
- 关键操作固定可点，模态框标题和按钮区不随正文滚动丢失。
- 金额默认显示 `¥••••`，由用户主动显示。
- 发布前端时必须同步 `index.html` 的 `?v=` 和 `sw.js` 缓存版本，避免新旧脚本混用。

**验收标准**

- 手机端表单、列表和弹窗无横向滚动，底部按钮可操作。
- 页面脚本版本不一致时提示强刷，不能表现为按钮无响应。
- 重新登录后金额恢复默认遮罩。

### REQ-DATA-001 · 数据审计、软删除、备份与数据库切换

**需求**

- 所有表必须有 `create_time`、`update_time`、`is_delete`；`is_delete=0` 表示有效，`is_delete=1` 表示已删除。
- 不允许使用数据库外键；关联完整性由应用服务和事务保证。
- 业务记录优先软删除，关键引用要阻止破坏性删除。
- 默认支持 SQLite，另支持 MySQL 8.0 和 `utf8mb4`。
- 备份必须覆盖数据库与本地附件，并验证可恢复；MySQL 部署使用对应备份手册。

**验收标准**

- 新建表及迁移后所有表都有三个标准字段。
- SQLite 与 MySQL 的标准字段规则一致；数据库健康信息不泄露密码。
- 备份包含数据库和上传目录，校验失败时保留上一份有效备份并告警。
- 数据库迁移在事务中执行，失败不产生半迁移业务数据。

### REQ-OPS-001 · 健康检查与部署回滚

**需求**

- 后端提供无需登录的健康检查。
- 支持 systemd + nginx 传统部署，也支持单镜像 Docker 部署。
- 关停或回滚 CRM 不得影响同机的其他服务。
- 发布、备份、恢复和回滚步骤必须可复现。

**验收标准**

- `/health` 返回状态、数据库类型和当前时间，不返回凭据。
- `/crm/` 静态页和 `/crm/api/crm/*` 接口在容器与反向代理模式均可访问。
- 服务启动失败时可以从日志定位到迁移、依赖或配置问题。
- 回滚前先保留当前现场，回滚后健康检查通过。

## 6. 非目标与已取消口径

以下内容不属于当前版本：

- 多用户、公海池、角色权限、审批流。
- 生产工单、生产排程、库存管理和工厂设备对接。
- 财务系统直连、发票系统、合同系统和退款支付接口。
- 多日日程、邮件或短信订阅提醒。
- 客户页面常规手工新增。
- 售后“拒绝”和终态重开。
- 订单取消、退款状态分支；退款或退货通过售后单记录。
- 多产品订单 V1 中“生成订单后待客户确认再赢单”的旧流程；已由报价单确认流程替代。
- 早期商机阶段“需求确认 / 成交洽谈 / 赢单”以及旧物流值 `carrier`。

## 7. 需求变更规则

新增或修改需求时：

1. 在本文件追加新的 `REQ-xxx`，或更新已有条目的状态和验收标准。
2. 在 `03-progress.md` 追加一条变更日志，写清来源和影响。
3. 若有模块、接口或数据结构变化，同步更新 `02-arch.md`。
4. 不删除历史需求；失效口径标记 ~~删除线~~，补充替代条目和原因。
5. 每次修改后刷新三份文档的“最后更新”日期。
